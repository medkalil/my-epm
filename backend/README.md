### Flyway Database Migrations

**Flyway** is an open-source database migration and version control tool for relational databases. It manages schema evolution predictably across development, testing, and production environments without requiring manual DDL execution.

#### 1. How Flyway Executes
- **Startup Integration:** Flyway integrates directly into Spring Boot via `flyway-core`. Upon starting the application (`mvn spring-boot:run`), Flyway automatically executes **before** Spring Data JPA / Hibernate initializes the `EntityManagerFactory`.
- **Script Location:** Flyway scans `src/main/resources/db/migration/` for versioned SQL scripts.
- **Naming Convention:** Migration files must strictly adhere to the pattern:
  `V<Version>__<Description>.sql` (e.g., `V1__init_auth_schema.sql`, `V2__init_organization_schema.sql`).
- **Execution Order:** Flyway parses the version numbers numerically and executes unapplied migrations sequentially inside database transactions.

#### 2. Tracking & History (`flyway_schema_history`)
Flyway creates and maintains a system tracking table in PostgreSQL named `flyway_schema_history`. For every migration applied:
- It records the script version, description, checksum (hash of file contents), execution timestamp, and success state.
- Before executing any pending script, Flyway validates local SQL files against the recorded checksums in `flyway_schema_history` to prevent undetected schema tampering.

#### 3. Managing Table Structures (Create, Update, Delete)
Flyway follows an **append-only, version-controlled model**. Once a migration script has been executed on a target database, it must remain immutable.

- **Creating Tables & Structures:**
  Write a new versioned SQL script containing `CREATE TABLE`, `CREATE INDEX`, or `CREATE SEQUENCE` statements.
  *Example (`V1__init_auth_schema.sql`):*
  ```sql
  CREATE TABLE users (
      id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
      name VARCHAR(255) NOT NULL,
      password VARCHAR(255) NOT NULL
  );
  ```

- **Updating / Altering Existing Tables:**
  **Do not edit an existing migration file that has already run.** Instead, create a new higher-version file (e.g., `V3__add_avatar_to_users.sql`):
  ```sql
  ALTER TABLE users ADD COLUMN avatar_url VARCHAR(500);
  ALTER TABLE organizations ALTER COLUMN name SET DATA TYPE VARCHAR(150);
  ```

- **Deleting Tables, Columns, or Constraints:**
  Create a new versioned script to drop schema components (e.g., `V4__drop_legacy_tables.sql`):
  ```sql
  ALTER TABLE users DROP COLUMN legacy_col;
  DROP TABLE temp_logs;
  ```

#### 4. Handling Checksum Mismatches & Errors
If a migration file that was already applied is modified, Flyway will detect a checksum mismatch and throw a `FlywayValidateException` on application startup.
- **Repair Schema History:** Run the repair command to sync updated local checksums into the database:
  ```bash
  mvn flyway:repair -Dflyway.url=jdbc:postgresql://localhost:5432/epm_db -Dflyway.user=postgres -Dflyway.password=postgres
  ```
- **Local Dev Reset:** Alternatively, drop and recreate the development database (`dropdb epm_db && createdb epm_db`).



### Authentication System

The authentication system uses JWT access tokens and database-backed refresh tokens:

- **Register:** `POST /api/v1/auth/register` (Registers a new user account)
- **Login:** `POST /api/v1/auth/login` (Returns JWT access token & refresh token)
- **Refresh Token:** `POST /api/v1/auth/refreshtoken` (Generates a new access token using a valid refresh token)

#### How It Works:
1. **Registration:** User submits credentials; password is hashed with BCrypt and stored in PostgreSQL.
2. **Authentication:** User logs in; server returns a short-lived JWT access token and saves a long-lived UUID refresh token in the database.
3. **Authorization:** Client sends `Authorization: Bearer <JWT_ACCESS_TOKEN>` in HTTP headers. `AuthTokenFilter` validates the signature and sets authentication context.
4. **Token Refresh:** When the access token expires, client sends the refresh token to `/api/v1/auth/refreshtoken` to receive a new access token.

### Organization System (SaaS Multi-Tenancy)

Organizations act as multi-tenant customer workspaces:

- **Create Organization:** `POST /api/v1/organizations` (Creates organization and sets creator as `OWNER`)
- **Get User Organizations:** `GET /api/v1/organizations/my` (Lists all organizations the user belongs to)
- **Get Organization by ID:** `GET /api/v1/organizations/{id}`
- **Get Organization by Slug:** `GET /api/v1/organizations/slug/{slug}`
- **Add Member:** `POST /api/v1/organizations/{id}/members` (Adds user with role: `ADMIN`, `MEMBER`, `GUEST`)
- **Get Members:** `GET /api/v1/organizations/{id}/members` (Lists members of an organization)
